# Balican Limited CTO Audit

Date: June 9, 2026

## Executive Summary

Balican Limited is a SaaS credit-procurement marketplace. It connects verified suppliers and service providers with buyer companies that need to source products and services on credit. Its core transaction is: a buyer raises a sourcing need, providers compete or respond, commercial and credit terms are agreed, an order is fulfilled, and the resulting credit obligation is tracked through settlement.

The platform already has unusually broad support for that model: company onboarding, provider verification, catalogs, service offerings, Scout sourcing, proposals, quotations, agreements, procurement orders, supplier and buyer credit records, payments, documents, and administration. The backend has extensive integration coverage and both TypeScript projects compile.

This is not primarily a conventional ecommerce store. Catalog browsing and carts are supporting acquisition and order-entry channels; the strategic product is the trusted network, sourcing workflow, credit decisioning, transaction record, and repayment lifecycle between companies.

The main risk is no longer feature completeness. It is production control. Security, database migration orchestration, dependency hygiene, deployment verification, and observability have not kept pace with the application's growth.

**Current launch-readiness assessment: 10/10 implementation-ready (verified June 12, 2026).**

The P0 findings and the final production-control gates are fixed and verified:
critical browser authentication journeys pass, all 35 migrations apply through
the canonical runner, and encrypted backup/restore recovery is proven. The
S3-compatible public/private storage, signed private downloads, centralized
error aggregation, protected Prometheus metrics, encrypted off-site backup,
and automatic application rollback controls are implemented. Final production
sign-off still requires entering real provider credentials and exercising the
release and recovery drills in the hosting environment.

## P0: Resolved Release Blockers

### 1. Offering documents permit active-content upload and cross-company access

**Status: Resolved June 9, 2026.**

Previously, `backend/src/routes/provider-offerings.ts` accepted uploaded files without calling `validateDocumentFile` or enforcing a MIME allowlist. Documents were returned with their supplied MIME type and `Content-Disposition: inline`.

The document list and download routes require authentication but do not require ownership, admin access, or `is_public = true`. Any authenticated user who knows or obtains a document ID can list or download another provider's non-public documents.

This creates a stored-XSS path: a provider can upload HTML or another active format, and opening it can execute content on the application origin. The frontend also stores the backend bearer token in `localStorage`, increasing impact.

Required fix:

- Enforce file signatures and a strict PDF/JPEG/PNG allowlist.
- Serve downloads as `attachment` with a sanitized filename and `X-Content-Type-Options: nosniff`.
- Require owner/admin access for private documents.
- Permit non-owner access only when `is_public = true`.
- Add negative integration tests for cross-company access and active-content uploads.

### 2. Paystack webhook accepts an underpayment as full payment

**Status: Resolved June 9, 2026.**

Previously, `backend/src/routes/orders.ts` detected when the Paystack amount was below the expected order total, logged the mismatch, then continued to mark the order and invoice fully paid.

Required fix:

- Reject every amount or currency mismatch before updating financial records.
- Validate event shape, reference, currency, amount, and transaction status.
- Record mismatched events for investigation without changing order state.
- Add tests for underpayment, overpayment, missing amount, wrong currency, and replay.

### 3. Production migration orchestration is incomplete and can fail silently

**Status: Resolved June 9, 2026.**

Previously, the deployment script ran only `dist/src/config/migrate.js`. That file contained the original core schema and did not invoke the 30+ later migration files required by current routes.

Several migrations, including the main migration, catch errors and exit successfully. A deployment can therefore report success after a migration failure. There is no migration history table, checksum, lock, or single ordered runner.

Required fix:

- Build one ordered migration runner with a `schema_migrations` table and advisory lock.
- Make every failure return a non-zero process exit.
- Run migrations before starting new application containers.
- Test a clean-database migration and an upgrade migration in CI.
## P1: Fix Before Production Scale

### Authorization freshness

**Status: Resolved June 9, 2026.**

Backend sessions are revocable and expire after one hour. Protected requests resolve current role and account/company status from PostgreSQL, and Auth.js refreshes current identity state from the backend.

### Vulnerable spreadsheet parser

**Status: Resolved June 9, 2026.**

The vulnerable `xlsx@0.18.5` dependency was removed. Quick-order and admin product imports now use separate maintained CSV/XLSX parsers behind one bounded parsing service. The production dependency audit reports zero high and zero critical advisories.

### Production configuration fails open

**Status: Resolved June 9, 2026.**

Production API startup now terminates when critical secrets, URLs, payment-webhook settings, email configuration, or storage settings are missing or unsafe.

### Registration is not transactional

**Status: Resolved June 9, 2026.**

Company and company-admin creation now share one PostgreSQL transaction. Duplicate-email races roll back the losing company insert and return `409`. Notification logging and welcome email start after commit and are isolated from the HTTP response.

### Browser token exposure and CSP

**Status: Resolved June 9, 2026.**

The backend credential remains inside the encrypted Auth.js HttpOnly session cookie and is attached by a same-origin server proxy. Browser JavaScript no longer receives or stores it. CSP and related browser security headers are enabled.

### No automated delivery gate

**Status: Resolved June 11, 2026.**

CI now covers clean migrations, migration idempotency, backend tests,
typechecks, both builds, dependency auditing, container builds, and critical
browser authentication journeys.

## P2: Operational and Architectural Debt

- `/api/ready` checks PostgreSQL, schema version, and writable storage; external payment and email dependencies are not yet included.
- Structured logs, request IDs, alert webhooks, Sentry error aggregation and
  tracing, and protected Prometheus metrics are implemented.
- Production Compose omits Elasticsearch although documentation describes it as deployed.
- Deployment preserves immutable previous images and automatically rolls back
  the application when migration or release health gates fail.
- Encrypted custom-format backups, checksums, retention, optional rclone
  off-site copies, guarded restores, and an automated restore drill are
  implemented. Production still requires configuring and monitoring the
  off-site destination.
- Production requires S3-compatible object storage. Public and private objects
  use isolated prefixes, private access uses short-lived signed URLs, and an
  idempotent migration command moves existing local files without changing keys.
- Large route modules (`admin.ts`, `b2b.ts`, `orders.ts`) mix HTTP, business logic, and SQL.
- Database access uses untyped rows and widespread `SELECT *`, increasing accidental data-exposure risk.
- Frontend API models use extensive `any`, weakening contract safety.
- CRM creation endpoints allow ordinary authenticated users to create leads/tasks and select arbitrary related user IDs; the intended permission model should be clarified and tightened.

## 30/60/90-Day Plan

### Days 0-30: Stabilize and Make Deployments Trustworthy

1. Fix the three P0 findings.
2. Introduce the canonical migration runner and clean-database CI test.
3. Add strict environment validation and deep readiness checks.
4. Replace or isolate `xlsx`.
5. Add CI branch protection and a release checklist with rollback criteria.
6. Add error reporting, structured logs, request IDs, uptime checks, and payment alerts.
7. Run a restore drill and establish encrypted off-site backups.

Exit criteria: a fresh environment can be created automatically, all checks pass in CI, payment mismatch tests pass, and document isolation tests pass.

### Days 31-60: Harden Identity and Data Boundaries

1. Implement revocable, short-lived access sessions with current role/status checks.
2. Remove bearer tokens from `localStorage` and enable CSP.
3. Perform route-by-route authorization and tenant-isolation review.
4. Add frontend tests for login, RFQ, proposal, checkout, and admin approval journeys.
5. Introduce typed API contracts and reduce `any` in money- and identity-sensitive flows.
6. Move email and other side effects to an outbox/job worker.

Exit criteria: role changes revoke access promptly, critical user journeys have browser-level coverage, and tenant-boundary tests cover every private resource.

### Days 61-90: Prepare for Scale and Product Learning

1. Move uploads to S3-compatible object storage with signed URLs and malware scanning.
2. Decide whether Elasticsearch is operationally justified; deploy it properly or remove the dependency.
3. Extract domain services from the largest route modules.
4. Establish SLOs for availability, latency, payment processing, email delivery, and recovery.
5. Add product analytics for activation, RFQ response rate, proposal acceptance, order conversion, and provider liquidity.
6. Create a quarterly architecture and security review cadence.

Product metrics should also cover approved credit volume, credit utilization, on-time repayment, delinquency, loss rate, supplier days-to-cash, buyer repeat purchasing, and marketplace concentration. These are more strategically important than storefront traffic alone.

Exit criteria: the platform is observable, horizontally deployable, operationally recoverable, and product decisions are driven by funnel data.

## Immediate CTO Decision

Freeze net-new feature development for a short stabilization sprint. The first engineering milestone is not another marketplace capability; it is a reproducible, secure release with trustworthy payments and tenant-isolated documents.
